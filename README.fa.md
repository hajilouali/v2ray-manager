# v2rm

[🇬🇧 English documentation](README.md)

**v2rm** یک ابزار خط‌فرمان (CLI) ساده و کاربرپسند برای مدیریت [Xray-core](https://github.com/XTLS/Xray-core) و [sing-box](https://github.com/SagerNet/sing-box) روی لینوکس است. این ابزار همان کارهایی که در v2rayN (کلاینت گرافیکی ویندوز) انجام می‌دهید را در ترمینال در اختیارتان می‌گذارد: افزودن کانفیگ از روی لینک‌های اشتراک‌گذاری یا فایل‌های کامل JSON مربوط به Xray، افزودن و به‌روزرسانی لینک‌های ساب (Subscription)، ویرایش کانفیگ‌ها، تست واقعی سالم‌بودن یک کانفیگ، و جابجایی راحت بین اتصال‌ها — همه در یک ابزار کوچک.

**v2rm هرگز تنظیمات پروکسی سراسری سیستم را دست نمی‌زند.** با اتصال، فقط یک پروکسی SOCKS5 و HTTP روی `127.0.0.1` (یا روی آدرسی که خودتان با `v2rm port set --listen` تعیین می‌کنید) بالا می‌آید و بس. فقط برنامه‌هایی که صراحتاً به این پورت وصل‌شان کنید از پروکسی استفاده می‌کنند؛ بقیه‌ی سیستم شما دقیقاً مثل قبل و بدون واسطه به اینترنت وصل می‌ماند.

## امکانات

- **افزودن کانفیگ** از روی لینک‌های `vmess://`، `vless://` (شامل VLESS+REALITY)، `trojan://`، `ss://` (هم فرمت SIP002 و هم فرمت قدیمی)، `hysteria2://`/`hy2://`، `tuic://` و `masque://` — تکی، از روی فایل، یا از ورودی استاندارد (stdin). لینک‌ها می‌توانند گزینه‌های جدیدتر Xray را هم داشته باشند: `fp=unsafe`، `cs` (cipher suite ها)، `ech`، `fm` (finalmask، یعنی قطعه‌قطعه‌کردن TLS hello)، `mode`/`extra` در XHTTP، رمزنگاری پساکوانتومی VLESS (`encryption`)، `headers` و `packetEncoding` (بخش «گزینه‌های لینک» را ببینید).
- **کانفیگ‌های کامل Xray به‌صورت JSON (پروفایل «خام» یا raw)**: یک کانفیگ کامل Xray — فایل، آرایه‌ای از چند کانفیگ، یا یک ساب JSON — اضافه کنید و v2rm آن را همان‌طور که هست اجرا می‌کند و فقط inbound هایش را عوض می‌کند تا تضمین‌های پروکسی محلی v2rm سر جایشان بمانند. بخش «کانفیگ‌های خام Xray (JSON)» را ببینید.
- **پروفایل‌های MASQUE (روی HTTP/2)** برای Xray-core: `v2rm add masque ...`. بخش «MASQUE» را ببینید.
- **ساب (Subscription)**: یک لینک ساب اضافه کنید و بعداً به‌روزش کنید. فرمت را خودکار تشخیص می‌دهد: JSON مربوط به Xray، لیست ساده‌ی لینک‌ها (حتی با کامنت‌های سرآیند `#profile-title` و `#profile-update-interval`)، لیست بیس۶۴، یا YAML کلش/Mihomo. اگر انتهای آدرس `#name` بگذارید، همان نام ساب می‌شود و هرگز به سرور فرستاده نمی‌شود. هنگام به‌روزرسانی، لیست جدید با کانفیگ‌های موجود مقایسه می‌شود: نودهای تازه اضافه، نودهای حذف‌شده برداشته، و بقیه سرجایشان به‌روز می‌شوند — تشخیص بر اساس هویت واقعی سرور است نه اسم، پس اگر ارائه‌دهنده اسم یک نود را عوض کند، نه کپی تکراری ساخته می‌شود و نه اتصال فعال شما به‌هم می‌ریزد.
- **ویرایش کانفیگ‌ها**، هم با فلگ‌های `--نام‌فیلد` برای فیلدهای پرکاربرد، هم با باز کردن کل پروفایل (YAML، یا کانفیگ JSON برای پروفایل خام) در `$EDITOR`.
- **تست واقعی اتصال**: دستور `v2rm test` فقط پینگ نمی‌گیرد — یک نمونه‌ی موقت از هسته را بالا می‌آورد، از طریق آن وصل می‌شود، و واقعاً یک فایل کوچک دانلود می‌کند تا تأخیر (latency) و سرعت واقعی را گزارش بدهد. با `test --all` همه‌ی پروفایل‌های ذخیره‌شده به‌صورت موازی تست و بر اساس سرعت مرتب می‌شوند.
- **جابجایی اتصال** در یک دستور، به‌صورت زنده، با `v2rm connect <profile>` یا `v2rm profile use <profile>`.
- **فقط پروکسی محلی SOCKS و HTTP.** هیچ‌وقت از TUN استفاده نمی‌شود و تنظیمات پروکسی سیستم/NetworkManager دست نمی‌خورد. با `v2rm env` می‌توانید فقط یک ترمینال را وارد حالت پروکسی کنید (`eval "$(v2rm env)"`)، یا با `v2rm exec -- <command>` فقط یک دستور را از طریق پروکسی اجرا کنید — بقیه‌ی سیستم بی‌تغییر می‌ماند.
- **خودتان تعیین می‌کنید پروکسی روی کجا گوش بدهد**: loopback (پیش‌فرض)، یک آدرس مشخص، bridge داکر (`--listen docker`) یا همه‌ی اینترفیس‌ها (`0.0.0.0`) — با نام‌کاربری/رمز اختیاری (`--auth USER:PASS`)، هشدار وقتی پروکسی فراتر از localhost در دسترس است، و دستور `doctor` که به فایروال شما هم نگاه می‌کند. بخش «استفاده از v2rm داخل داکر» را ببینید.
- **دو هسته‌ی قابل تعویض** — Xray-core و sing-box — که با `v2rm core` نصب، به‌روزرسانی و جابجا می‌شوند. sing-box علاوه بر این، از Hysteria2 و TUIC هم پشتیبانی می‌کند که Xray-core آن‌ها را ندارد؛ در عوض MASQUE، کانفیگ‌های خام و گزینه‌های جدیدتر لینک فقط با Xray-core کار می‌کنند.
- **قوانین روت (Routing)**: پیش‌فرض‌های آماده‌ی `global` (همه چیز از پروکسی)، `bypass-cn` (همان حالت کلاسیک v2rayN برای دور زدن چین)، و `bypass-ir` (سایت‌ها و آی‌پی‌های ایرانی و شبکه‌ی محلی مستقیم، بقیه از تونل)، به‌علاوه‌ی یک فایل قانون سفارشی که خودتان می‌نویسید.
- **منوی تعاملی دوستانه** (کافی است `v2rm` را بدون آرگومان اجرا کنید) برای استفاده‌ی روزمره — شامل «Add a JSON config» و «Add a MASQUE server» — که پشت‌صحنه از همان دستورات خط‌فرمان استفاده می‌کند.

## نصب

نیازمند Python نسخه‌ی ۳.۱۰ یا بالاتر روی لینوکس است.

```bash
git clone https://github.com/hajilouali/v2ray-manager.git
cd v2ray-manager
./install.sh
```

اسکریپت `install.sh` اول اگر [pipx](https://pipx.pypa.io/) نصب نباشد خودش نصبش می‌کند، بعد v2rm را با آن نصب می‌کند، و در پایان `pipx ensurepath` را اجرا می‌کند — یعنی دیگر لازم نیست دستی چیزی به `PATH` اضافه کنید. (مثل هر تغییر `PATH`ای، فقط در ترمینال‌های *جدید* اثر می‌کند — خودِ اسکریپت در پایان می‌گوید که آیا لازم است ترمینال را باز کنید یا فایل rc شل‌تان را `source` کنید.)

ترجیح می‌دهید دستی نصب کنید؟ `pipx install .` هم دقیقاً همین کار را می‌کند؛ `pip install --user .` هم کار می‌کند ولی `PATH` را برایتان درست **نمی‌کند** — اگر بعدش دستور `v2rm` پیدا نشد، تقریباً همیشه همین است: pip فایل اجرایی را در `~/.local/bin` می‌گذارد که همیشه در `PATH` نیست، مخصوصاً برای کاربر `root`. با این دستور حلش کنید: `echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc && source ~/.bashrc`؛ یا به‌جایش با `pip install .` ساده به‌صورت سراسری نصب کنید.

سپس حداقل یکی از هسته‌ها را نصب کنید:

```bash
v2rm core install xray
# و/یا
v2rm core install singbox
```

کانفیگ‌های خام، MASQUE و چند گزینه‌ی لینک به یک Xray-core جدید نیاز دارند. Xray-core فعلاً جدیدترین نسخه‌هایش را فقط به‌صورت *pre-release* در GitHub منتشر می‌کند و نصب‌کننده‌ی v2rm مگر اینکه بخواهید آن‌ها را نادیده می‌گیرد؛ پس `v2rm core update xray --pre` را اجرا کنید (دستور ساده‌ی `core update xray` نسخه‌ی stable قدیمی‌تر را می‌دهد)، بعد با `v2rm doctor` ببینید Xray شما دقیقاً چه چیزهایی را پشتیبانی می‌کند.

دستورهای `core install` و `core update` نسخه را از API گیت‌هاب می‌پرسند که برای هر آی‌پی فقط ۶۰ درخواست ناشناس در ساعت می‌دهد؛ روی سرور یا شبکه‌ای که آی‌پی مشترک دارد این سهمیه راحت تمام می‌شود. اگر پیام «rate limit exceeded» دیدید، تا زمان ریستی که چاپ می‌کند صبر کنید یا `GITHUB_TOKEN` را export کنید (هر توکنی، حتی بدون هیچ دسترسی، سقف را به ۵۰۰۰ در ساعت می‌رساند). توکن فقط به API فرستاده می‌شود، هرگز همراه دانلودها.

## شروع سریع

```bash
# افزودن کانفیگ از روی لینک
v2rm add "vless://uuid@host:443?security=reality&sni=example.com&pbk=...&sid=...&flow=xtls-rprx-vision#My Server"

# ...یا یک کانفیگ کامل Xray به‌صورت JSON (یک آبجکت، یا آرایه‌ای از آبجکت‌ها)
v2rm add --json config.json
curl -s https://example.com/config.json | v2rm add --json -

# ...یا یک سرور MASQUE (روی HTTP/2)
v2rm add masque --server masque.example.com --sni front.example.com --user alice --pass 's3cret' --path /masque

# یا افزودن یک ساب
v2rm sub add "https://provider.example.com/sub/abc123" --name myprovider

# دیدن لیست کانفیگ‌ها و سرعت واقعی هرکدام
v2rm profile list
v2rm test --all

# اتصال
v2rm connect "My Server"
v2rm status

# وصل کردن فقط یک برنامه به پروکسی -- هیچ‌چیز سراسری عوض نمی‌شود
curl --socks5-hostname 127.0.0.1:10808 https://example.com
# یا برای کل یک نشست ترمینال:
eval "$(v2rm env)"
curl https://example.com    # حالا از پروکسی رد می‌شود
exit                         # برگشت به ترمینال عادی

v2rm disconnect
```

اگر به‌جای حفظ‌کردن فلگ‌ها منو را ترجیح می‌دهید، کافی است `v2rm` را بدون هیچ آرگومانی اجرا کنید.

| دستور | توضیح |
|---|---|
| `v2rm` یا `v2rm menu` | اجرای منوی تعاملی |

| `v2rm add --json FILE` یا `add --json -` | افزودن یک کانفیگ کامل Xray به‌صورت JSON (یک آبجکت، یا آرایه‌ای از آن‌ها) |
| `v2rm add masque --server H --sni S [--port P] [--alpn h2] [--user U --pass P] [--path /x] [--host H] [--header 'K: V' ...] [--fp chrome] [--name N]` | افزودن یک سرور MASQUE |

| `v2rm profile show <id> [--link\|--json]` | نمایش یک پروفایل، چاپ دوباره‌اش به‌شکل لینک، یا چاپ داده‌ی ذخیره‌شده‌اش به‌صورت JSON |
| `v2rm profile edit <id> [--name ...] [--server ...] ...` | ویرایش فیلدها؛ بدون فلگ، `$EDITOR` باز می‌شود (برای پروفایل خام، کانفیگ JSON) |
| `v2rm profile remove <id> [--yes] [--force]` | حذف یک پروفایل |
| `v2rm profile rename <id> <name>` | تغییر نام پروفایل |
| `v2rm profile use <id>` | تعیین پروفایل فعال (در صورت اتصال، جابجایی زنده) |

| `v2rm sub list` یا `sub show <id>` | لیست/جزئیات ساب‌ها |
| `v2rm route show [--preset P]` | نمایش قوانین روت فعال (یا یک پیش‌نمایش) |
| `v2rm route set <global\|bypass-ir\|bypass-cn\|custom>` | تغییر پیش‌فرض روت |
| `v2rm route edit` | ویرایش فایل قوانین روت سفارشی |
| `v2rm route update-data [--force]` | به‌روزرسانی دیتابیس GeoIP/GeoSite برای Xray-core |
| `v2rm core list` | لیست نسخه‌های نصب‌شده‌ی هسته‌ها |
| `v2rm core install <xray\|singbox> [--version V \| --pre]` | دانلود و نصب یک هسته (`--pre`: جدیدترین نسخه حتی اگر pre-release باشد) |
| `v2rm core update <xray\|singbox> [--pre]` | به‌روزرسانی به آخرین نسخه؛ هرگز به نسخه‌ی قدیمی‌تر برنمی‌گردد (`--pre` نسخه‌های pre-release را هم در نظر می‌گیرد) |
| `v2rm core use <xray\|singbox>` | تعیین هسته‌ی پیش‌فرض |
| `v2rm core remove <xray\|singbox> [--version V] [--all]` | حذف نسخه(های) نصب‌شده |
| `v2rm port show` | نمایش آدرس گوش‌دادن، پورت‌ها و اینکه نام‌کاربری/رمز لازم است یا نه |
| `v2rm port set [--socks P] [--http P] [--listen ADDR\|docker] [--auth USER:PASS \| --no-auth]` | تغییر پورت‌ها، آدرس گوش‌دادن و نام‌کاربری/رمز پروکسی محلی |

همه‌ی دستورات `--help` دارند.

## گزینه‌های لینک

لینک‌های اشتراک‌گذاری می‌توانند گزینه‌هایی فراتر از موارد پایه داشته باشند. v2rm این‌ها را روی پروفایل نگه می‌دارد، در کانفیگ Xray می‌نویسد و در `profile show --link` دوباره در لینک خروجی می‌آورد:

| پارامتر لینک | کاری که v2rm می‌کند |
|---|---|
| `fp` | اثرانگشت TLS، همان‌طور که نوشته شده منتقل می‌شود (`chrome`، `firefox`، `unsafe`، …) |
| `cs` | cipher suite های TLS، جداشده با دونقطه ← `tlsSettings.cipherSuites` |
| `ech`، `echConfigList`، `echcl` | تنظیم ECH (هر سه املا) ← `tlsSettings.echConfigList` |
| `fm` (JSON با URL-encode) | `streamSettings.finalmask` (قطعه‌قطعه‌کردن TLS hello، noise، …) |
| `type=xhttp`، `mode`، `extra` (JSON) | ترنسپورت XHTTP؛ `mode` و `extra` داخل `xhttpSettings` می‌روند |
| `encryption=mlkem768x25519plus…` | رمزنگاری پساکوانتومی VLESS ← فیلد `encryption` کاربر (به‌جای اجبار `none`) |
| `headers` (JSON یا لیست `k:v`) | هدرهای درخواست برای ws / httpupgrade / xhttp. هدر `Host` به `host` خودِ ترنسپورت تبدیل می‌شود |
| `packetEncoding`، `packet-encoding` | sing-box: نگاشت می‌شود (`xudp`، `packetaddr`). Xray-core برای VLESS همیشه از XUDP استفاده می‌کند؛ مقادیر دیگر هنگام اتصال یادآوری می‌شوند |
| `fragment` (قدیمی، sockopt) | روی پروفایل نگه داشته می‌شود ولی اعمال نمی‌شود — `connect` این را می‌گوید؛ به‌جایش از `fm` استفاده کنید |
| `headerType` | هر مقداری غیر از `none` نگه داشته و هنگام اتصال یادآوری می‌شود (مبهم‌سازی هدر TCP تولید نمی‌شود) |

sing-box نمی‌تواند finalmask، ECH، XHTTP/KCP، رمزنگاری پساکوانتومی VLESS یا اثرانگشت‌هایی را که نمی‌شناسد بیان کند. به‌جای اینکه بی‌صدا حذفشان کند و پروفایلی را وصل کند که بعداً عجیب رفتار می‌کند، v2rm با یک پیام که می‌گوید از Xray-core استفاده کنید، رد می‌کند. به همین ترتیب Xray-core فعلی ترنسپورت‌های `http` (h2) و `quic` و گزینه‌ی `allowInsecure` را حذف کرده؛ لینک‌هایی که به این‌ها تکیه دارند به‌جای ساخت کانفیگی که Xray رد می‌کند، یک خطای روشن می‌گیرند.

## کانفیگ‌های خام Xray (JSON)

بعضی کانفیگ‌ها اصلاً سرور ندارند. معروف‌ترینشان نوع «serverless» است: یک کانفیگ کامل Xray که فقط از outbound های `direct`/`block`/`dns`، قطعه‌قطعه‌کردن TLS ClientHello (`finalmask`)، fake DNS، DoH و روت‌های سفارشی استفاده می‌کند. این را نمی‌شود به‌صورت «سرور + پورت» بیان کرد، پس v2rm کل JSON را به‌عنوان یک **پروفایل خام (raw)** نگه می‌دارد (نوع `raw`، با `—` به‌جای سرور).

```bash
v2rm add --json config.json              # یک آبجکت کانفیگ، یا آرایه‌ای از آن‌ها (هرکدام یک پروفایل می‌شود)
v2rm add --json -  < config.json         # از stdin
v2rm sub add "<آدرس یک ساب JSON>"
v2rm profile show <id> --json            # چاپ کانفیگ ذخیره‌شده (با `add --json -` دوباره قابل افزودن است)
v2rm profile edit <id>                   # JSON را در $EDITOR باز می‌کند؛ JSON نامعتبر یا نبودن لیست "outbounds" را نمی‌پذیرد
```

نام پیش‌فرض، مقدار `"remarks"` کانفیگ است.

**v2rm چگونه آن را اجرا می‌کند.** JSON ذخیره‌شده هرگز عیناً اجرا نمی‌شود. v2rm کانفیگ زمان اجرا را از روی یک کپی می‌سازد و *فقط inbound ها* را تغییر می‌دهد:

- فقط inbound های `socks`، `http` و `mixed` نگه داشته می‌شوند. هر چیز دیگر (`tun`، `dokodemo-door`، `tproxy`، …) حذف می‌شود، با یک هشدار تک‌خطی که می‌گوید چه چیزی حذف شده.
- v2rm فقط یک inbound پروکسی نگه می‌دارد (inbound های SOCKS/HTTP اضافه با همان هشدار حذف می‌شوند). این inbound روی آدرسی که با `v2rm port set --listen` تعیین کرده‌اید بسته می‌شود — همیشه به‌صورت صریح نوشته می‌شود، چون کانفیگ‌های نمونه معمولاً `listen` ندارند و Xray در آن حالت پشت سر شما روی `0.0.0.0` گوش می‌دهد — و روی پورت SOCKS خودِ v2rm. (کانفیگی که فقط یک inbound از نوع `http` دارد، آن را روی پورت HTTP خودِ v2rm نگه می‌دارد و یک inbound SOCKS هم کنارش اضافه می‌شود.)
- پورت HTTP خودِ v2rm با یک inbound از نوع `http` که اضافه می‌شود (برچسب `<original-tag>-http`، همان آدرس گوش‌دادن، همان بلوک `sniffing`) سرویس داده می‌شود و این برچسب به هر لیست `routing.rules[].inboundTag` که برچسب اصلی را دارد اضافه می‌شود، تا روت‌های کانفیگ با هر دو یکسان رفتار کنند. inbound از نوع `mixed` خودش هر دو را روی پورت SOCKS سرویس می‌دهد. کانفیگی که inbound قابل‌استفاده ندارد، یک جفت SOCKS + HTTP معمولی می‌گیرد.
- اگر برای پروکسی نام‌کاربری/رمز گذاشته باشید (`--auth`)، همه‌ی inbound ها آن را لازم دارند.
- `dns`، `outbounds`، `routing`، `policy`، `fakedns`، `observatory`، balancer ها، کلیدهای ناشناخته و `version` دقیقاً همان‌طور که نوشته شده‌اند می‌مانند.
- شنونده‌هایی که از `inbounds` نمی‌آیند — یعنی `metrics.listen` و `api.listen` — هم همان‌طور که نوشته شده‌اند می‌مانند، ولی `connect` و `test` در یک یادداشت اسمشان را می‌آورند، چون بیرون از آدرسی هستند که شما انتخاب کرده‌اید.
- **پیش‌فرض‌های روت اعمال نمی‌شوند.** پروفایل خام روت خودش را دارد؛ `v2rm route show`، `route set`، `status` و `connect` این را صریحاً می‌گویند، نه اینکه وانمود کنند یک پیش‌فرض اثر دارد.
- **همیشه Xray-core**، هرچه `v2rm core use` گفته باشد. اگر sing-box هسته‌ی پیش‌فرض شما باشد، v2rm برای این پروفایل به Xray سوییچ می‌کند و در یک خط می‌گوید (هسته‌ی پیش‌فرض شما عوض نمی‌شود).
- **بررسی نسخه.** اگر کانفیگ `"version": {"min": …, "max": …}` داشته باشد، v2rm آن را به‌صورت عددی با نسخه‌ی نصب‌شده‌ی Xray مقایسه می‌کند (`26.6.27` و `v26.10.17` هر دو کار می‌کنند) و اگر نخواند، می‌گوید `v2rm core update xray --pre` را اجرا کنید.
- **اعتبارسنجی پیش از اجرا.** قبل از شروع — در `connect` و در `test` — v2rm دستور `xray run -test -c <file>` را با `XRAY_LOCATION_ASSET` اشاره‌کننده به دیتای geo خودش اجرا می‌کند و خروجی خطای خودِ Xray را نشان می‌دهد، به‌علاوه‌ی یک راهنمایی برای دلایل رایج: تگ ناشناخته‌ی `geosite:`/`geoip:` (دستور `v2rm route update-data --force` را اجرا کنید) یا هسته‌ی قدیمی.
- `v2rm test` روی پروفایل‌های خام هم مثل بقیه کار می‌کند، با همان بازنویسی روی پورت‌های موقت.

### کانفیگ «serverless» چیست — و چه چیزی نیست

کانفیگ serverless **هیچ سرور راه‌دوری ندارد**. *مستقیم* وصل می‌شود و سعی می‌کند فیلترینگ مبتنی بر بازرسی عمیق بسته (DPI) را دور بزند (مثلاً با قطعه‌قطعه‌کردن TLS ClientHello). این یعنی دور زدن DPI روی اتصال عادی خودتان، **نه VPN و نه تونل**: وب‌سایت‌ها همچنان آی‌پی واقعی شما را می‌بینند و هر چیزی که *بر اساس آی‌پی* مسدود شده باشد، همچنان مسدود می‌ماند. فقط جایی کمک می‌کند که مسدودسازی با بررسی handshake/SNI انجام می‌شود. وقتی چنین کانفیگی را `v2rm test` می‌کنید، قبولی یعنی «اتصال مستقیم با آن روش دور زدن کار می‌کند» — v2rm هم در خروجی همین را می‌گوید.

## MASQUE (روی HTTP/2)

MASQUE ترافیک را روی HTTP CONNECT عبور می‌دهد. کلاینت Xray-core هم حالت **HTTP/2** (Extended CONNECT روی TLS) را دارد و هم HTTP/3؛ v2rm به‌صورت پیش‌فرض HTTP/2 را انتخاب می‌کند (`alpn` برابر `h2`؛ اگر `h3` هم پیشنهاد شود، HTTP/3 انتخاب می‌شود). پروفایل‌های MASQUE فقط روی Xray-core اجرا می‌شوند — `connect` خودکار آن را انتخاب می‌کند و sing-box با یک پیام روشن رد می‌کند.

```bash
v2rm add masque --server masque.example.com --port 443 --sni front.example.com \
  --user alice --pass 's3cret' --path /masque --header 'X-Token: abc' --fp chrome --name MyMasque
```

| گزینه | معنی |
|---|---|
| `--server`، `--port` (پیش‌فرض ۴۴۳) | پروکسی MASQUE |
| `--sni` | نام سرور TLS که ارائه می‌شود |
| `--alpn` (پیش‌فرض `h2`) | `h2` = حالت HTTP/2؛ `h3` = HTTP/3؛ برای پیشنهاد چند مقدار با کاما جدا کنید |
| `--user`، `--pass` | نام‌کاربری/رمز Basic (هر دو را با هم بدهید) |
| `--path`، `--host` | مسیر درخواست (با `/` شروع می‌شود؛ `{target}`/`{ipproto}` مجاز است) و authority |
| `--header 'K: V'` | هدر اضافه‌ی درخواست، تکرارپذیر (`Host`/`Capsule-Protocol` مجاز نیستند؛ `Authorization` هم همراه `--user`/`--pass` مجاز نیست) |
| `--fp` | اثرانگشت TLS برای تقلید |
| `--name` | نام نمایشی (پیش‌فرض `host:port`) |

v2rm هنگام افزودن پروفایل همان قواعدی را بررسی می‌کند که کانفیگ MASQUE خودِ Xray-core بررسی می‌کند، پس اشتباه‌ها همان لحظه با یک پیام خوانا معلوم می‌شوند، نه به‌صورت خطای شروع هسته. اگر Xray شما آن‌قدر قدیمی باشد که MASQUE را نشناسد، اعتبارسنجی پیش از اجرا این را می‌گوید و پیشنهاد می‌کند `v2rm core update xray --pre` را اجرا کنید (`v2rm doctor` هم همین را گزارش می‌دهد).

**لینک `masque://` قرارداد اختصاصی خودِ v2rm است، نه یک استاندارد رایج در اکوسیستم** — جای دیگری فرمت لینک اشتراک‌گذاری برای MASQUE وجود ندارد. v2rm این را تولید و تجزیه می‌کند:

```
masque://[user:pass@]host:port?sni=&alpn=h2&fp=&path=&host=&headers=<JSON با URL-encode>&fm=<JSON با URL-encode>#name
```

(به‌علاوه‌ی `dns=` اختیاری — آی‌پی‌های resolver جداشده با کاما برای `remoteDNS` در Xray — و `warp=<JSON با URL-encode>`). دستور `profile show <id> --link` آن را چاپ می‌کند تا بتوانید پروفایل را به اشتراک بگذارید یا پشتیبان بگیرید. یک کانفیگ کامل Xray که outbound اش `masque` است هم از مسیر خام بالا کار می‌کند.

## ساب (Subscription)

```bash
v2rm sub add "https://raw.githubusercontent.com/patterniha/Serverless-for-Iran/refs/heads/main/Subscription/Serverless-for-Iran.json#Patterniha-S"
v2rm sub add "https://raw.githubusercontent.com/patterniha/Free-Configs/main/configs.txt#Patterniha-F"
v2rm sub list
v2rm sub update --all
```

- متنِ بعد از `#` **نام** ساب می‌شود (`Patterniha-S`، `Patterniha-F`). پیش از دریافت از آدرس جدا می‌شود — هرگز به سرور فرستاده نمی‌شود. `--name` آن را بازنویسی می‌کند؛ اگر هیچ‌کدام نباشد، v2rm از کامنت سرآیند `#profile-title:` و بعد از نام هاست استفاده می‌کند.
- **فرمت‌ها** از روی بدنه و به این ترتیب تشخیص داده می‌شوند: JSON مربوط به Xray (یک آبجکت با لیست `outbounds`، یا آرایه‌ای از آن‌ها ← برای هرکدام یک پروفایل خام)، YAML کلش/Mihomo، لیست بیس۶۴، لیست ساده‌ی لینک. خط‌هایی که با `#` شروع می‌شوند کامنت‌اند و بررسی بیس۶۴ را گمراه نمی‌کنند؛ `#profile-title` و `#profile-update-interval` (به ساعت) خوانده می‌شوند و بازه توسط `sub show` نمایش داده می‌شود.
- `sub update --all` همیشه به‌روزرسانی می‌کند. با `--respect-interval` (برای cron مفید است) ساب‌هایی که تازه‌تر از بازه‌ی خودِ ارائه‌دهنده به‌روز شده‌اند رد می‌شوند؛ اضافه‌کردن `--force` این را دوباره بی‌اثر می‌کند (و اجازه می‌دهد به‌روزرسانی، پروفایل متصل فعلی را هم حذف کند).
- **یک نود، چند نسخه.** بعضی لیست‌ها هر نود را چند بار می‌آورند که فقط در اثرانگشت / cipher suite / قطعه‌قطعه‌سازی / ECH فرق دارند. v2rm این‌ها را پروفایل‌های جدا حساب می‌کند (هویت‌شان SNI، host، path، نوع شبکه و یک هش از همین پارامترها را شامل می‌شود، ولی هرگز نام را نه)، پس هیچ‌کدام گم یا رونویس نمی‌شود، و به‌روزرسانی یک بدنه‌ی تغییرنکرده هیچ چیزی اضافه یا حذف نمی‌کند. پروفایل خام با `remarks` اش تشخیص داده می‌شود، پس کانفیگی که محتوایش عوض شده ولی `remarks` اش همان است، سرجایش به‌روز می‌شود.
- اگر یک به‌روزرسانی چیز قابل‌استفاده‌ای نیاورد (صفحه‌ی خطای سرور، پاسخ ناقص)، پروفایل‌های موجود پاک نمی‌شوند و حفظ می‌شوند.

## پیش‌فرض‌های روت (Routing)

- **`global`** (پیش‌فرض): هرچه به پروکسی می‌رسد، از همان مسیر خارج می‌شود. هیچ قانون دور زدنی وجود ندارد.
- **`bypass-ir`**: سایت‌ها و آی‌پی‌های ایرانی و آدرس‌های شبکه‌ی محلی/خصوصی مستقیم می‌روند؛ بقیه از تونل رد می‌شوند.
- **`bypass-cn`**: همان حالت کلاسیک پیش‌فرض v2rayN — چین و آدرس‌های خصوصی/محلی مستقیم می‌روند.
- **`custom`**: دستور `v2rm route edit` یک فایل YAML با توضیحات باز می‌کند (`~/.config/v2rm/routes/custom.yaml`) که در آن قوانین `direct`/`block` را بر اساس پسوند دامنه، کلیدواژه‌ی دامنه، دسته‌ی geosite، بازه‌ی آی‌پی، یا کد GeoIP می‌نویسید.

پیش‌فرض‌ها روی پروفایل‌های مبتنی بر لینک اعمال می‌شوند. **پروفایل‌های خام روت خودشان را دارند و پیش‌فرض‌ها را نادیده می‌گیرند** (بخش بالا را ببینید).

روتینگ بر اساس فرآیند (اینکه کدام برنامه درخواست را زده) به‌صورت دستور مستقل ارائه نشده — چون با کل فلسفه‌ی طراحی «پروکسی محلی SOCKS/HTTP» هم‌پوشانی دارد (شما از قبل مشخص می‌کنید کدام برنامه از پروکسی استفاده کند)، و روی لینوکس نسبتاً شکننده و وابسته به پلتفرم است. کاربران حرفه‌ای همچنان می‌توانند قوانین `process_name`/`process_path` را مستقیماً در `custom.yaml` بنویسند — sing-box از این‌ها به‌صورت بومی پشتیبانی می‌کند.

به‌طور آگاهانه هیچ حالت TUN یا پروکسی سراسری هم وجود ندارد — دلیلش را در بخش پرسش‌های متداول ببینید.

## هسته‌ها: Xray-core در برابر sing-box

| پروتکل / قابلیت | Xray-core | sing-box |
|---|---|---|
| VMess | ✅ | ✅ |
| VLESS (شامل REALITY) | ✅ | ✅ |
| Trojan | ✅ | ✅ |
| Shadowsocks | ✅ | ✅ |
| Hysteria2 | ❌ | ✅ |
| TUIC | ❌ | ✅ |
| MASQUE | ✅ | ❌ |
| کانفیگ‌های خام Xray (JSON) | ✅ | ❌ |
| finalmask، ECH، XHTTP، رمزنگاری پساکوانتومی VLESS (`encryption`) | ✅ | ❌ (با پیام روشن رد می‌شود) |

دستور `v2rm connect` از هسته‌ی پیش‌فرض شما استفاده می‌کند (Xray-core، مگر اینکه `v2rm core use singbox` زده باشید)، با این استثنا که پروفایل‌هایی که فقط یک هسته می‌تواند اجرا کند، خودکار همان هسته را می‌گیرند و یک یادداشت تک‌خطی می‌بینید: پروفایل‌های خام و MASQUE ← Xray-core، و Hysteria2/TUIC ← sing-box. اتصال‌دادن هرگز هسته‌ی پیش‌فرض ذخیره‌شده‌ی شما را عوض نمی‌کند.

## محل فایل‌های تنظیمات و داده

همه در مسیرهای استاندارد XDG (قابل تغییر با `V2RM_CONFIG_HOME`/`V2RM_DATA_HOME`/`V2RM_STATE_HOME`/`V2RM_CACHE_HOME`):

- `~/.config/v2rm/` — پروفایل‌ها (شامل کانفیگ‌های خام)، ساب‌ها، وضعیت برنامه، `routes/custom.yaml`، و `auth.json` (نام‌کاربری/رمز پروکسی، با دسترسی `0600`؛ عمداً در `v2rm export` گذاشته نمی‌شود)
- `~/.local/share/v2rm/bin/` — فایل‌های اجرایی هسته‌های نصب‌شده
- `~/.local/state/v2rm/run/` — کانفیگ تولیدشده در زمان اجرا (با دسترسی `0600`، چون اطلاعات ورود سرور شما را دارد)، pidfile، لاگ هسته
- `~/.cache/v2rm/assets/` — دیتای GeoIP/GeoSite ذخیره‌شده

## استفاده از v2rm داخل داکر

`127.0.0.1` داخل کانتینر، loopback خودِ کانتینر است؛ پس با تنظیم پیش‌فرض (`127.0.0.1`) کانتینرها **نمی‌توانند** به پروکسی v2rm برسند. اینکه پروکسی روی کجا گوش بدهد تصمیم خودتان است، با `v2rm port set --listen` تعیین می‌شود و هیچ‌جا ثابت‌نوشته (hard-code) نشده:

| `--listen` | از کجا در دسترس است | کی استفاده کنیم |
|---|---|---|
| `127.0.0.1` (پیش‌فرض) | فقط همین هاست | وقتی هیچ کانتینری به پروکسی نیاز ندارد |
| `docker` | کانتینرهای روی bridge پیش‌فرض داکر (v2rm آدرس را پیدا می‌کند، معمولاً `172.17.0.1`، و چاپ می‌کند) | راه‌اندازی سریع برای bridge پیش‌فرض |
| یک آدرس مشخص، مثلاً `172.18.0.1` | هر چیزی که به آن آدرس برسد | یک شبکه‌ی مشخص |
| `0.0.0.0` | همه‌ی اینترفیس‌ها و همه‌ی شبکه‌های داکر، چه موجود و چه آینده | پروژه‌های compose (هرکدام شبکه‌ی خودش را می‌سازد) — حتماً با فایروال و/یا `--auth` |

v2rm بررسی می‌کند که یک آدرس مشخص واقعاً روی این هاست وجود داشته باشد (`0.0.0.0` و `::` همیشه قبول‌اند)، و هنگام `connect` هم دوباره بررسی می‌کند — آدرس bridge داکر فقط تا وقتی داکر روشن است وجود دارد.

```bash
v2rm port set --listen docker                          # چاپ می‌کند: Docker bridge address: 172.17.0.1 ...
# یا برای پوشش همه‌ی شبکه‌ها:
v2rm port set --listen 0.0.0.0 --auth demo:demo-pass
v2rm connect
```

> `--listen docker` bridge **پیش‌فرض** را پیدا می‌کند (`docker network inspect bridge`، و در صورت شکست، آدرس اینترفیس `docker0`). کانتینرهای روی شبکه‌های دیگر گیت‌وی خودشان را دارند (`172.18.0.1`، `172.19.0.1`، …) و فایروال باید ساب‌نت آن‌ها را هم اجازه بدهد؛ اگر یکی از آن‌ها نتوانست وصل شود، `docker network inspect <network>` را ببینید — یا از `0.0.0.0` استفاده کنید.

### وصل کردن یک کانتینر به پروکسی

```bash
# بلوک متغیرهای محیطی برای کانتینر (روی stdout چاپ می‌شود و هشدارها روی stderr، پس ریدایرکت‌کردنش امن است):
v2rm env --docker > proxy.env           # از آدرس bridge استفاده می‌کند
v2rm env --host host.docker.internal    # یا یک نام؛ بلوک شامل HTTP_PROXY=http://host.docker.internal:10809 و ... می‌شود

docker run --rm --env-file proxy.env curlimages/curl -I https://example.com

# با استفاده از نام (داکر ۲۰.۱۰ به بالا روی لینوکس): host-gateway همان آدرس bridge پیش‌فرض است
docker run --rm --add-host=host.docker.internal:host-gateway \
  curlimages/curl -x http://demo:demo-pass@host.docker.internal:10809 -I https://example.com
```

docker compose:

```yaml
services:
  app:
    image: your/app
    extra_hosts:
      - "host.docker.internal:host-gateway"
    environment:
      HTTP_PROXY: http://demo:demo-pass@host.docker.internal:10809     # اگر نام‌کاربری/رمز نگذاشته‌اید "demo:demo-pass@" را بردارید
      HTTPS_PROXY: http://demo:demo-pass@host.docker.internal:10809
      ALL_PROXY: socks5h://demo:demo-pass@host.docker.internal:10808
      NO_PROXY: localhost,127.0.0.1,::1,host.docker.internal           # ترافیک به خودِ هاست از پروکسی رد نشود
```

دستورات `v2rm env --docker` و `env --host ...` دقیقاً چنین بلوکی را چاپ می‌کنند و اگر نام‌کاربری/رمز گذاشته باشید داخل آدرس‌ها می‌آید (پس آن فایل را خصوصی نگه دارید). `v2rm env` و `v2rm exec` روی خودِ هاست از آدرسی که پروکسی واقعاً روی آن بسته شده استفاده می‌کنند و نام‌کاربری/رمز را هم می‌گذارند، و `v2rm test` هم آن را می‌فرستد.

### نام‌کاربری/رمز و فایروال

هر چیزی که به یک آدرس گوش‌دادنِ غیر-loopback برسد می‌تواند از اتصال شما استفاده کند، مگر اینکه محافظتش کنید. v2rm **فقط هشدار می‌دهد و هرگز انتخاب شما را مسدود نمی‌کند**: وقتی پروکسی فراتر از localhost گوش می‌دهد، `connect`، `status`، `port set` و `doctor` یک هشدار تک‌خطی چاپ می‌کنند، و اگر نام‌کاربری/رمزی هم نگذاشته باشید می‌گویند پروکسی باز است و دستورات فایروال مربوطه را هم نشان می‌دهند:

```bash
# ufw: بازه‌های خصوصی داکر را اجازه بدهید، بقیه را ببندید
sudo ufw allow from 172.16.0.0/12 to any port 10808,10809 proto tcp
sudo ufw deny 10808,10809/tcp        # فقط وقتی لازم است که سیاست پیش‌فرض‌تان ترافیک ورودی را اجازه می‌دهد

# یا iptables (بدون iptables-persistent / netfilter-persistent بعد از ریبوت از بین می‌روند)
sudo iptables -A INPUT -s 172.16.0.0/12 -p tcp -m multiport --dports 10808,10809 -j ACCEPT
sudo iptables -A INPUT -p tcp -m multiport --dports 10808,10809 -j DROP
```

- `--auth USER:PASS` باعث می‌شود هر دو پورت SOCKS و HTTP همین نام‌کاربری/رمز را بخواهند (روی همه‌ی inbound ها، برای هر نوع پروفایل و برای هر دو هسته). در `auth.json` با دسترسی `0600` ذخیره می‌شود و جز داخل آدرس‌های پروکسی که خودتان می‌خواهید (`env`، `env --docker`) هرگز چاپ نمی‌شود. نام‌کاربری/رمز SOCKS5 و HTTP بدون رمزنگاری فرستاده می‌شود، پس روی localhost یا bridge داکر مشکلی ندارد ولی در شبکه‌ی غیرقابل‌اعتماد نه. `--no-auth` آن را برمی‌دارد.
- `v2rm doctor` هم وقتی بتواند قوانین ufw/iptables را بخواند به آن‌ها نگاه می‌کند و می‌گوید پورت‌های پروکسی باز، محدودشده یا بسته‌اند. خواندن قوانین فایروال معمولاً دسترسی root می‌خواهد و nftables/firewalld/security group های ابری پوشش داده نمی‌شوند — وقتی نتواند تشخیص بدهد، به‌جای حدس‌زدن می‌گوید «couldn't determine».

## پرسش‌های متداول

**چرا پروکسی سراسری یا حالت TUN وجود ندارد؟** این یک تصمیم طراحی عمدی است. v2rm فقط یک پروکسی SOCKS/HTTP محلی بالا می‌آورد؛ تا وقتی خودتان صراحتاً چیزی را به آن وصل نکنید (با `v2rm env`، `v2rm exec`، یا تنظیمات پروکسی خودِ برنامه)، هیچ ترافیکی از سیستم شما مسیرش عوض نمی‌شود. اگر دنبال تونل‌کردن کل سیستم هستید، این ابزار برای آن ساخته نشده.

**کانفیگ serverless یک VPN است؟** نه. بخش «کانفیگ serverless چیست — و چه چیزی نیست» را ببینید: DPI را روی یک اتصال مستقیم دور می‌زند؛ آی‌پی شما دیده می‌شود و سایت‌های مسدودشده‌ی بر اساس آی‌پی همچنان مسدود می‌مانند.

**کانفیگ را از کجا بگیرم؟** از هرکسی که سرور مقصد شما را اداره می‌کند — به‌صورت یک لینک اشتراک‌گذاری یا یک لینک ساب — یا، برای کانفیگ‌های خام، از کسی که آن‌ها را منتشر می‌کند.

## توسعه

```bash
pip install -e ".[dev]"
pytest
```

همه‌ی تست‌ها بجز آن‌هایی که واقعاً یک هسته را اجرا و به اینترنت واقعی وصل می‌شوند (با نشان `integration`، که به‌صورت پیش‌فرض اجرا نمی‌شوند) به‌صورت آفلاین و قطعی اجرا می‌شوند و از نمونه‌های واقعی ساب که زیر `tests/fixtures/` ذخیره شده‌اند استفاده می‌کنند.

تست‌های integration دستور واقعی `xray run -test` را روی کانفیگ‌هایی که v2rm تولید می‌کند اجرا می‌کنند (هیچ‌چیز شروع یا وصل نمی‌شود): یک پروفایل serverless روی چند آدرس گوش‌دادن، پروفایل‌های MASQUE، و همه‌ی لینک‌های نمونه‌ی واقعی.

```bash
V2RM_INTEGRATION=1 V2RM_XRAY=/path/to/xray pytest tests/integration
# اختیاری: V2RM_GEO_ASSETS=~/.cache/v2rm/assets  (پوشه‌ای که `v2rm route update-data` پر می‌کند)
```
